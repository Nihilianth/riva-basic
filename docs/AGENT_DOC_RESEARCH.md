# Research: AGENTS.md and agent documentation/skills best practices

Date: 2026-10-31. Reference for epic `nqd` (documentation findability: agent
entry-point routing, skill triggers, knowledge surfacing). Compiled from
official specs and vendor docs plus practitioner guides; sources listed per
section and at the end.

## 1. AGENTS.md — a router, not an encyclopedia

Consensus model (agents.md spec; OpenStack nova/cinder contributor guides;
Atlan; HumanLayer/taim.io):

- The root file is a compact routing layer plus high-signal guardrails. It
  should contain "only information that is difficult for an agent to discover
  from source, config, or existing docs, and that is likely to prevent an
  incorrect action" (OpenStack).
- Appropriate content: pointers to authoritative contributor/testing/subsystem
  docs; guardrails for common incorrect actions not obvious from source.
- Explicitly listed as avoid (OpenStack): long-form explanations; summaries of
  docs that may drift from the source of truth; rules already enforced by
  linters/validation; personal preferences or in-progress notes.
- Length budgets: OpenStack prunes when the file approaches 100 lines;
  practitioner consensus is 60-300 lines (Atlan); Claude's memory guide says
  under 200 per file. Over 300 lines: split into references, nested files,
  rules, commands, or skills.
- Fit tests: "Every line should earn its place by preventing a concrete
  mistake" (agent-md-advisor); "if a rule does not change agent behavior when
  removed, it is probably noise."
- Two-Failure Rule (HumanLayer): one wrong choice may be task difficulty; the
  same wrong choice twice is durable ambiguity. Fix it with one exact path,
  command, or reference example, then rerun the task and compare.
- Recommended structure order (agent-md-advisor): project overview; tech
  stack; exact commands (fast file-scoped checks first); project structure and
  "where new code goes" rules; critical MUST/MUST-NOT rules; non-default
  conventions; testing/done criteria; safety and permissions (Always / Ask
  first / Never); reference documents with "Read when" triggers; good
  patterns and anti-patterns with real file paths.
- Progressive disclosure: deep docs get "Read when" triggers from the root
  file; prefer pointers to copies (copied snippets rot).
- Pitfalls (Atlan): autogenerated-from-/init files often perform worse than no
  file; restating what package.json/README already says; writing past the
  budget; conflicting tool-specific files (CLAUDE.md vs AGENTS.md) — pick one
  source of truth; vague boundaries.
- Mechanics (agents.md spec): no required fields; nested AGENTS.md per
  subproject, closest file wins; explicit user chat prompts override
  everything; agents attempt to run testing commands found in the file.

## 2. Skills — the description is the trigger

Anthropic (platform.claude.com skill authoring best practices; code.claude.com
skills docs; anthropics/skills skill-creator; Claude complete guide):

- `name` + `description` in the SKILL.md frontmatter are the ONLY parts that
  influence triggering. The body only matters after the skill loads.
- Description requirements: non-empty, max 1024 chars, third person ("it
  processes..." not "I can help..."), includes what the skill does AND when to
  use it, with concrete trigger phrases and file/type names.
- Boundaries belong in the description: "Not for X" clauses prevent
  over-triggering; sibling pointers ("not this — use that") prevent
  misrouting. The skill-creator guidance says make descriptions a little
  "pushy" to combat undertriggering ("use this whenever the user mentions ...
  even if they don't explicitly ask").
- Body: keep SKILL.md under 500 lines; once loaded, every token is a
  recurring cost across turns (it stays in context). Progressive disclosure:
  SKILL.md is a table of contents pointing to reference files loaded as
  needed.
- Evaluations first: run the agent on representative tasks without the skill,
  document the failures, build should-trigger/should-not-trigger query sets
  (negatives should be near-misses, not obviously irrelevant), establish a
  baseline, write minimal instructions, iterate.
- Trigger mechanics: Claude only consults skills for tasks it cannot easily
  handle alone; simple one-step queries may not trigger even with a perfect
  description. Multiple skills can activate for different aspects of one task.
- Name constraints: 1-64 chars, lowercase alphanumeric with single hyphens,
  must match the directory name (OpenCode adds this last rule).

## 3. OpenCode mechanics (project-relevant)

opencode.ai docs (rules, skills, agents; v2 docs instructions; Marginal
summary):

- V1: both AGENTS.md and CLAUDE.md recognized; first matching file wins per
  category — if both exist at the project, only AGENTS.md is used.
- V2: recognizes AGENTS.md ONLY; CLAUDE.md is not read as a fallback.
- Claude Code also reads a repository's AGENTS.md in place of CLAUDE.md.
  Conclusion: a duplicated CLAUDE.md is either unread (OpenCode) or a second,
  drifting source of truth (Claude Code with both present).
- Global rules: ~/.config/opencode/AGENTS.md (personal, not committed).
- The `instructions` array in opencode.json loads extra files, globs, or HTTP
  URLs as ambient instructions (5s fetch timeout), after AGENTS.md files.
- Instruction assembly order (v2): agent/provider system prompt; Code Mode
  tool guidance; MCP server/reference/skill guidance; global and project
  AGENTS.md plus configured instructions; built-in date/env context;
  session-specific instruction entries.
- Nested AGENTS.md below the workspace is discovered when the agent reads or
  lists files in that area; loaded nearest-first, deduplicated. Edits to a
  nested file after it loaded are NOT detected automatically — start a new
  session when updated text must apply immediately.
- Skills are discovered from .opencode/skills/, .claude/skills/,
  .agents/skills/ (project, walked up to the worktree root) plus global
  equivalents. Frontmatter: name (required, must match directory name),
  description (required, 1-1024 chars), license/compatibility/metadata
  optional. Skills are listed with name + description in the skill tool
  description and loaded on demand via the skill tool. Permissions
  (allow/deny/ask with wildcards) can gate skills per agent.
- OpenCode has no rules folder; extra instruction files come from the
  `instructions` key of opencode.json.

## 4. Claude Code memory conventions

code.claude.com memory + best-practices docs:

- CLAUDE.md: target under 200 lines; every line takes attention on every task.
  Hold only what Claude could not work out from the code: how to confirm work
  (exact test/typecheck/lint commands, how to run one test), places where the
  code is misleading, decisions not in the repo, anything corrected twice.
- Add-when rules: Claude makes the same mistake a second time; a code review
  catches something; the same correction is typed twice; a new teammate would
  need the context. Multi-step procedures or area-only rules move to skills or
  path-scoped rules.
- Imports (@path syntax) organize a long file but do NOT reduce context
  (imported files load inline with the importing file). Path-scoped rules
  (.claude/rules/) load only when Claude works with matching files.
- Layer by directory for large codebases: root file holds repo-wide rules;
  per-subsystem files load on demand.
- Instructions are context, not enforced configuration — hooks (PreToolUse,
  Stop) enforce. HTML block comments in CLAUDE.md are stripped before
  injection (notes for humans cost no context).
- Verification tooling: /context (what actually loaded), /doctor (suggests
  cuts for anything Claude can work out itself), /doctor prompt-audit (flags
  instructions written for older models, dead file pointers, contradictions).
  Claude Code only; OpenCode has no equivalent audit.

## 5. MCP tool descriptions

modelcontextprotocol.io client best practices; AWS prescriptive guidance;
GetMCP; dsplce "tool descriptions are prompts"; ACM TOSEM study:

- The description decides whether to call the tool, which tool when several
  match, and what arguments to supply. Recipe: start with a verb; state what
  it RETURNS (not just what it does); when to use it vs a sibling tool;
  parameter value shapes (YYYY-MM-DD, not "a date"), defaults, side effects,
  latency/cost signals.
- The "not this — use that" sibling pointer is repeatedly named the single
  most valuable sentence; explicitly ruling out incorrect use dramatically
  reduces wrong tool calls.
- Keep under ~200 words; avoid vague verbs (handles, manages, processes).
- One tool = one action; snake_case verb_noun names; consistent verbs.
- Progressive discovery (catalog search, inspect, execute) for large tool
  sets; thresholds at 1-5% of context.
- ACM TOSEM 2026 study: 97.1% of 856 analyzed MCP tool descriptions contain at
  least one smell; 56% fail to state purpose clearly. Augmenting descriptions
  improved task success (median +5.85 pp) but increased execution steps
  (+67.46%) — compact variants often preserve reliability with less overhead.

## 6. llms.txt (context)

llmstxt.org v2; agent-docs-spec; Mintlify/Fern docs:

- Hub-and-spoke: a small root index, links to detail; agents view/search then
  follow links; most-specific file wins for subpaths.
- Useful framing (daloyjs.dev): "llms.txt answers where to read. AGENTS.md
  answers how to edit." Four separate jobs: AGENTS.md + skills (edit time),
  llms.txt + .md pages (public docs), OpenAPI (contract), MCP (runtime).
  Validates keeping edit-time routing in AGENTS.md rather than duplicating
  docs-site conventions into the repo.

## 8. Implications for nqd.1-nqd.5

- nqd.1 (AGENTS.md routing table): form it as "Read when" trigger rows
  (question/incident -> exact document, skill or MCP), one line per row, near
  the top of the file where it is guaranteed to be read. Add the Two-Failure
  Rule as the maintenance trigger: a row is added when the same question fails
  twice. Resolve the CLAUDE.md drift (owner decision: one-line pointer file vs
  in-step with a drift check vs retire). Note the length trade-off: the
  routing table adds ~15-20 lines to an already-over-budget file; middle path
  is routing at the top plus periodic pruning of state sections into bd
  tickets/memories.
- nqd.2 (skill descriptions): rewrite as pushy third-person descriptions with
  explicit sibling pointers. asset-search's description should END with
  "maps/levels/Blueprints -> kismet-llm, never guess a name"; kismet-llm's
  should point back to asset-search for spawnable meshes. mcp-interplay's
  trigger should name operational work (restart, travel, pick a map) even when
  not asked about "research".
- nqd.3 (mcp-interplay body): keep terse — once loaded the body is a
  recurring token cost; state rules, not explanations.
- nqd.4 (operational docs block): matches the hub-and-spoke/routing-index
  pattern; one line per pointer with exact file names.
- nqd.5 (findings rule): the rule IS the Two-Failure Rule plus Claude's
  "add when the same mistake twice"; findings go to the relevant subsystem
  record and the existing ticket as comments/notes as they happen.
- Optional, not scheduled: trigger-eval query sets for the three fixed skills
  (skill-creator pattern); v2 idea: nested per-subsystem AGENTS.md files
  (python/chivalry2/, python/lib/ue4ss/) loaded on exploration; experiment
  with the opencode.json `instructions` array (e.g., load docs/subsystems/
  README.md) at the cost of tokens every session.
